0 Executive Summary

v1.1 revision. Stack decisions (Puck, Neon, Drizzle, Vercel) are approved. Direction change: this is a flexible, widget-style builder, not a site auto-generated from FieldPie data. A new site is initialized the tenant's way — template, AI, or blank — with FieldPie data as an optional prefill only. AI content generation lands as Phase 1.5. Auth is abstracted and the tenant is decoupled from a FieldPie account.
v1.2 revision (2026-08-04). Hosting and Postgres moved to Railway (host + database), replacing Vercel and Neon Postgres. Neon is retained only for object storage + AI gateway. The DB driver is now node-postgres. Cloudflare still fronts published sites for CDN and custom domains. Where sections below say "Vercel" or "Neon Postgres," read Railway; DEVELOPMENT_LOG.md is the authoritative current stack.

We are building a single-codebase, multi-tenant website builder. One deployment serves thousands of tenant sites.

Each tenant gets a free subdomain (customer.fieldpie.site) and can optionally connect a custom domain with automatic SSL. Site content is stored as structured JSON (not static HTML), edited through a visual block editor, and rendered server-side / statically for SEO and performance. The key differentiator is speed-to-live through a flexible builder: the tenant assembles a site from a curated block set with drag-and-drop reordering, add/remove sections, and full control of colors and fonts. To avoid a cold start, a new site is initialized three ways — pick a starter template, generate content with AI, or start blank — the tenant chooses. Where FieldPie holds low-variance data (business name, phone, address, hours) we can optionally prefill it, but content is driven by the builder and AI, not auto-generated from the account, because a tenant's offerings vary too much to seed reliably.

The recommended stack: Next.js (App Router) + TypeScript strict, Puck as the visual editor, Neon for Postgres, Drizzle as the ORM, and Vercel for early-stage hosting with a documented self-host migration path. Cloudflare for SaaS handles custom hostnames and SSL.

This plan deliberately stops before implementation. Section 8 lists the exact decisions I need you to confirm before any code is written.

1 Tech Stack — Recommendations, Tradeoffs, Decisions

For each open decision I give a recommendation, the reasoning, the main tradeoff, and what confirming it commits us to. These are the four decisions I most need locked before Phase 1.

1.1 Framework — Next.js App Router + React + TypeScript (strict)

Not an open decision. Next.js App Router gives us server components, static generation, per-route caching, and middleware — exactly the primitives multi-tenant site rendering needs. TypeScript strict is mandatory; any requires written justification.

1.2 Visual Editor — Puck recommended vs GrapesJS

DimensionPuckGrapesJS
ModelReact-native; renders your own React componentsFramework-agnostic; manipulates HTML/CSS in an iframe
OutputClean, portable JSON component treeHTML + CSS strings (plus its own JSON model)
Fit with Next.js/ReactNative — editor & runtime share componentsAdapter needed; render HTML, not React
Design-system controlHigh — you define the allowed blocksLower — freeform HTML/CSS invites drift
Maturity/ecosystemYounger, smaller communityOlder, larger, more plugins
Security surfaceStructured props → easy to validateFreeform HTML/CSS → larger surface
Recommendation: Puck. Our product is intentionally constrained — a curated block set (hero, services, reviews, gallery, contact), not a freeform HTML canvas. Puck persists a clean JSON tree, and the same components render the public site: one source of truth, strong typing, a small auditable sanitization surface.

Main tradeoff: Puck is younger; we accept more responsibility for building block components. Acceptable because our block set is small and we want to own it anyway.

1.3 Postgres host — Neon recommended vs Supabase

DimensionNeonSupabase
Core offeringServerless Postgres (autoscale, branching)Postgres + Auth + Storage + Realtime + RLS
DB branchingYes — first-classLimited
AuthNone (we use FieldPie auth)Built-in (we do not want parallel auth)
StorageNone (we use S3-compatible)Built-in (likely unused)
Serverless/edge fitExcellentGood
Lock-inLow — "just Postgres"Higher — value is the platform
Recommendation: Neon. We already use FieldPie auth (no parallel auth) and S3-compatible storage — removing the two biggest reasons to pick Supabase. What remains is Postgres, and Neon is the cleaner, lower-lock-in, serverless-native option with branching that makes migration testing safer.
Note on RLS: Neon doesn't stop us adding Postgres Row-Level Security as defense-in-depth later. Our primary isolation guarantee is the application data-access layer; RLS can be layered on top.

1.4 ORM — Drizzle recommended vs Prisma

DimensionDrizzlePrisma
StyleSQL-first, thin, TS-native query builderSchema-DSL + generated client
Serverless cold-startVery light; excellentHeavier engine; improving
Multi-tenant filteringExplicit SQL → easy to force tenant_idAbstraction can hide the filter
Migrationsdrizzle-kit (SQL-visible)Prisma Migrate (mature, polished)
Ecosystem/maturityYounger, fast-growingVery mature, great DX
Recommendation: Drizzle. SQL-first, low overhead, plays well with Neon's serverless driver, and — critically for our hard rule that every tenant-scoped query filters by tenant_id — keeps queries explicit and easy to wrap in a mandatory tenant-scoped data-access layer.

Main tradeoff: Prisma has more mature migrations and a larger ecosystem; Drizzle asks the team to be comfortable closer to SQL. Our standards already value explicit, auditable data access.

1.5 Hosting — Vercel now + documented self-host path recommended

DimensionVercel (early)Self-host VPS + Cloudflare CDN (scale)
Time to shipFastest — native Next.jsSlower — we own the ops
Custom domains at scaleWorks; per-domain cost adds upCheaper per domain at volume
Cost curveLow small, steepens with traffic/domainsHigher upfront, cheaper at scale
ControlLess infra controlFull control
Recommendation: Start on Vercel; document (don't build) the self-host migration path now. Vercel ships Phase 1 fastest. Because published sites are statically generated and CDN-cached, visitor traffic mostly bypasses origin regardless of host, softening Vercel's cost curve and de-risking the eventual migration.

2 High-Level System Architecture

Two pipelines matter: the visitor read path and the editor → publish write path. A third concern — initializing a new site (template, AI, or blank) — feeds the write path at onboarding.

2.1 Visitor request flow (hostname → tenant → content → render)

Visitor
  │  GET https://acme-plumbing.com/services   (or acme.fieldpie.site/services)
  ▼
CDN edge (cache)
  │  cache HIT  ──────────────► serve cached static HTML  (origin not hit)
  │  cache MISS
  ▼
Next.js middleware  ── resolves Host header → tenant
  │   1. read Host header
  │   2. look up domain in `domains` table (custom domain OR *.fieldpie.site)
  │   3. map → tenant_id (+ site_id)
  │   4. attach tenant context; 404 if unknown host
  ▼
Route handler / Server Component
  │   5. load PUBLISHED site + page JSON for (tenant_id, path)   [tenant-scoped]
  │   6. resolve design tokens (brand colors/fonts/logo) → CSS variables
  │   7. render Puck JSON tree → HTML with shared block components
  │   8. inject SEO (title, meta, OG, LocalBusiness JSON-LD)
  ▼
Static HTML response  → cached at CDN edge for subsequent visitors

Tenant resolution happens once in middleware; every downstream read is tenant-scoped; visitor traffic is served from the CDN; only the published state is ever visible.

2.2 Editor → JSON storage → publish → live pipeline

Tenant admin (authenticated via FieldPie auth/session)
  │  opens the site editor for their tenant
  ▼
Editor (Puck)  ── loads DRAFT page JSON
  │   edits blocks; autosave writes DRAFT  (draft never affects live)
  ▼
`pages`/`blocks` DRAFT state in Postgres  (tenant-scoped, sanitized)
  │  tenant clicks "Publish"
  ▼
Publish action
  │   1. validate + sanitize draft content
  │   2. copy DRAFT → PUBLISHED snapshot (versioned in `publish_states`)
  │   3. trigger revalidation of affected static paths
  │   4. purge CDN cache for those paths
  ▼
Live site serves the new PUBLISHED snapshot
Strict draft/published separation is a hard requirement: editing writes only to draft; visitors only ever see the last published snapshot. Publish is an explicit, atomic, versioned promotion (enabling rollback later).

2.3 Initializing a new site (template, AI, or blank)

When a tenant creates a site they choose how to start. We never force a blank page, but we also never assume the whole site can be derived from FieldPie data — offerings vary too much per tenant. All three strategies produce an editable draft in the same block-JSON model, so everything downstream (editor, publish, render) is identical:

Tenant chooses a start strategy
  │
  ├─ (a) Starter template  → pick an industry/style template
  │                          → its prebuilt section layout loads as the DRAFT
  │
  ├─ (b) AI content gen     → short intake (business type, services, tone)
  │                          → AI generates section copy + suggested layout
  │                            as the DRAFT; sections regenerate individually
  │
  └─ (c) Blank             → empty canvas; add sections from the block catalog

Optional prefill (any strategy, when data exists):
  FieldPie low-variance fields ──► business name, phone, address, hours
                                   → Contact block + LocalBusiness schema

After initialization the tenant works in the same flexible builder: drag-and-drop to reorder sections, add/remove blocks like widgets, swap photos, edit copy, and adjust colors and fonts via design tokens — then connect a domain and publish. Contact/request forms create leads in FieldPie where connected (internal leads otherwise). AI generation ships as Phase 1.5; Phase 1 delivers templates + blank + the full flexible builder.

3 Database Schema & Tenant Isolation

Postgres is the primary store. Content lives as structured JSON in blocks/pages. Field lists below are indicative and will be finalized in Phase 1, item 2.

3.1 Core tables

TablePurposeKey fields
tenantsOne row per builder customer (not necessarily a FieldPie account)id, fieldpie_account_id (nullable), name, status, timestamps
templatesReusable starter layouts for the "pick a template" pathid, name, industry, thumbnail_url, blocks (jsonb), is_system
sitesOne site per tenant (allow >1 later)id, tenant_id, name, default_locale, theme_tokens (jsonb), seo_defaults (jsonb)
pagesPages within a siteid, tenant_id, site_id, path, title, seo (jsonb), draft_blocks_id, published_blocks_id
blocksPuck JSON tree, versioned (the content)id, tenant_id, page_id, content (jsonb), kind (draft|published), version
domainsHostname → tenant/site mappingid, tenant_id, site_id, hostname (unique), type (subdomain|custom), verification_status, cloudflare_hostname_id, ssl_status, is_primary
media_assetsReferences to S3-compatible storageid, tenant_id, site_id, storage_key, url, alt_text, dimensions, mime_type, source (fieldpie|upload)
publish_statesAudit/version log of publishesid, tenant_id, site_id, page_id, published_blocks_id, published_by, published_at, note

3.2 Relationships

tenants 1─* sites 1─* pages 1─* blocks; sites 1─* domains; sites 1─* media_assets; pages 1─* publish_states. Every content table carries tenant_id directly (denormalized on purpose) so isolation never depends on a join being correct.

3.3 Tenant isolation strategy (security requirement)

  1. Data-access layer (primary control). All tenant data goes through a single TenantScopedDb wrapper constructed with a tenant_id that injects WHERE tenant_id = $current into every read and write. Application code cannot query content tables directly. Any query touching a tenant table without a tenant scope is a lint/review failure.
  2. Request context. Middleware resolves the tenant once and establishes an immutable tenant context. For admin/editor routes the tenant is derived from the FieldPie-authenticated session; cross-tenant access is rejected.
  3. Database RLS (optional hardening, later). On plain Postgres (Neon) we can add Row-Level Security keyed on a session variable as a backstop. Recommended for Phase 3, not required for Phase 1.

Additional rules: tenant_id and personal data never appear in URL params; user-authored content is sanitized before storage and again at render; media access is tenant-scoped.

4 Custom Domains & SSL (Cloudflare for SaaS)

4.1 Free subdomain: *.fieldpie.site (wildcard)

We provision a wildcard DNS record and a wildcard TLS certificate covering all subdomains. On tenant creation we insert a domains row (type = subdomain, verification_status = active immediately — no per-tenant DNS or cert work). Zero-friction, available at onboarding.

4.2 BYO custom domain: Cloudflare for SaaS (custom hostnames)

1. Tenant enters custom domain in the builder.
2. We call Cloudflare for SaaS "custom hostname" API → creates a custom
   hostname under our zone; store cloudflare_hostname_id, status = pending.
3. We show the DNS records to add at their registrar:
     - a CNAME (their domain → our Cloudflare SaaS target), and
     - a domain-control-validation (DCV) record for the certificate.
4. Tenant adds the records at their DNS provider.
5. Cloudflare validates ownership (DCV) and issues/renews SSL automatically.
6. We poll / receive status → when hostname + cert active,
   set verification_status = active, ssl_status = active.
7. Middleware now resolves the custom domain → tenant; CDN serves over HTTPS.
8. Certificate renewal is automatic (Cloudflare-managed) — no tenant action.

Cloudflare for SaaS is purpose-built for this: thousands of customer-owned hostnames terminating TLS under our infrastructure, with automated issuance and renewal.

4.3 Verification UX

The builder shows a domain status panel per custom domain: exact DNS records with copy buttons, a live status badge, a "Re-check" button that polls Cloudflare, and help text for common registrar mistakes. Subdomains show as Active immediately.

Pending→ Verifying→ Active/ Failed (with reason)

5 Repository Structure & Module Boundaries

A single Next.js repo with feature-based module boundaries (App Router, TypeScript):

fieldpie-website-builder/
├─ app/
│  ├─ (public)/                 # public tenant site rendering (SSR/SSG)
│  │  └─ [[...path]]/           # catch-all: tenant resolved via middleware
│  ├─ (admin)/                  # authenticated builder/editor UI (auth adapter)
│  │  ├─ start/                 # new-site init: template / AI / blank chooser
│  │  ├─ editor/                # Puck editor (drag-drop, add/remove sections)
│  │  ├─ domains/               # custom domain + verification UX
│  │  └─ settings/              # branding/theme (colors, fonts), SEO defaults
│  ├─ api/                      # route handlers (publish, forms→leads, domains)
│  ├─ sitemap.xml/route.ts      # per-tenant sitemap
│  └─ robots.txt/route.ts
├─ middleware.ts                # hostname → tenant resolution
├─ src/
│  ├─ blocks/                   # Puck block catalog (hero, services, reviews, gallery, contact)
│  ├─ editor/                   # Puck config, block registration
│  ├─ rendering/                # JSON tree → HTML, theme-token → CSS-var
│  ├─ tenancy/                  # tenant context, hostname resolver, TenantScopedDb
│  ├─ db/                       # Drizzle schema, migrations, query modules
│  ├─ domains/                  # Cloudflare-for-SaaS client, verification state machine
│  ├─ site-init/               # init strategies: template loader, prefill, blank
│  ├─ templates/                # starter template catalog + thumbnails
│  ├─ ai/                       # AI content generation (Phase 1.5): prompts, guardrails
│  ├─ auth/                     # auth adapter (FieldPie session + room for own signup)
│  ├─ fieldpie/                 # FieldPie API adapter (optional prefill + lead creation)
│  ├─ seo/                      # title/meta/OG/JSON-LD/sitemap scaffolding
│  ├─ media/                    # S3-compatible storage client, image handling
│  ├─ publish/                  # draft→published promotion, revalidate + purge
│  ├─ security/                 # sanitization (DOMPurify), input validation
│  └─ shared/                   # types, utils, design tokens
├─ tests/                       # tenant resolution, publish flow, domain verification
└─ README.md                    # what it does + how to run/test (American English)

Key boundaries: tenancy is the only module that establishes tenant context and owns TenantScopedDb; everything else receives a tenant-scoped db, never a raw one. blocks is shared between editor and rendering — one definition, two consumers. auth is an adapter supporting FieldPie session integration with room for an own-signup flow. fieldpie is an adapter for optional prefill and lead creation, isolating us from FieldPie's internal data model. site-init orchestrates the three start strategies but writes the same block-JSON as everything else. ai (Phase 1.5) is isolated so the LLM provider and prompts can evolve independently. publish is the only writer of published state. security centralizes sanitization so there's exactly one place to audit.

6 Phase 1 (MVP) — Ordered Work Items

Scope: subdomain-only sites, a flexible builder (drag-and-drop reordering, add/remove sections, color/font control), a small block set, init via template or blank (AI is Phase 1.5), and a request form that creates a lead. Custom domains are Phase 2 and excluded here. Each item is sized to be planned, approved, and implemented as its own step.

Phase 1 (MVP)

  1. Project scaffold + standards. Next.js App Router + TS strict, Tailwind + design tokens, lint/format, CI, README skeleton. No product logic.
  2. Database schema + Drizzle setup. Implement the eight tables (incl. templates); drizzle-kit migrations; connect Neon. Finalize field lists.
  3. Tenant context + TenantScopedDb. Isolation wrapper + request-scoped context, with tests proving cross-tenant access is impossible.
  4. Hostname → tenant middleware (subdomain). Resolve *.fieldpie.site; 404 unknown hosts; wildcard subdomain + cert configured.
  5. Block catalog v1 + theming. Hero, Services, Reviews, Gallery, Contact as typed React components usable in editor and runtime, themed via CSS variables (per-tenant colors/fonts).
  6. Public render path (SSR/SSG). Render published JSON → HTML with SEO scaffolding (title, meta, OG, LocalBusiness JSON-LD, sitemap, robots) and CDN caching.
  7. Flexible Puck editor (draft). Register block catalog; drag-and-drop reordering, add/remove sections, color/font controls; load/save draft JSON; autosave; strict draft/published separation.
  8. Publish flow. Atomic draft→published promotion, versioned; on-demand revalidation + CDN purge.
  9. Site initialization (template + blank) + start chooser. New-site flow: pick a starter template or start blank, both producing an editable draft; optional FieldPie prefill of contact fields where connected.
  10. Request form → lead. Contact block submits, sanitized/validated, creates a lead (via FieldPie adapter when connected; internal lead otherwise).
  11. Auth abstraction + tenant provisioning. Auth adapter supporting FieldPie session with room for own signup; tenant provisioned independently of a FieldPie account (fieldpie_account_id optional); reject cross-tenant.
  12. MVP hardening + tests + README. Critical-path tests, WCAG AA + mobile-first, performance budget (LCP, images), American-English run/test notes.

Phase 1.5 — AI content generation

An AI service that generates section copy and a suggested layout from a short intake (business type, services, tone), with per-section regenerate. New src/ai module: LLM provider, prompt design, cost controls, content guardrails/sanitization. Delivered right after the flexible builder so AI writes into a proven block model.

Suggested order: 1 → 2 → 3 → 4, then 5 → 6, then 7 → 8, then 9/10/11, then 12, then Phase 1.5. Each item is still gated individually.

7 Open Questions & Assumptions

Resolved in v1.1 (locked): site init is template / AI / blank, tenant's choice; the builder is fully flexible (drag-and-drop, add/remove sections, color/font control); AI is Phase 1.5; auth is abstracted and the tenant is decoupled from a FieldPie account (fieldpie_account_id optional), so the builder can later open to non-FieldPie users without a rewrite.

Assumptions (correct me if wrong)

  • FieldPie can, when a tenant is connected, expose an API to create a lead and read low-variance contact fields (name, phone, address, hours) for optional prefill. Full service/area/review seeding is no longer assumed.
  • FieldPie has an auth/session system we integrate with via the auth adapter — while keeping room for our own signup flow later.
  • We control fieldpie.site (or can acquire it) and can set up wildcard DNS + wildcard TLS.
  • We have a Cloudflare account eligible for Cloudflare for SaaS, and an S3-compatible object store.
  • One site per tenant for Phase 1 (schema allows more later).

Open questions (helpful, no longer blocking the core build)

  1. FieldPie prefill + lead API. For a connected tenant, which fields can we read for prefill, and what is the API/shape/auth to create a lead? (items 9–10 + the fieldpie adapter)
  2. Auth details. Session cookie / JWT / SSO, so we can build the adapter. Not committing to FieldPie-only vs. open signup yet. (item 11)
  3. AI provider & budget (Phase 1.5). Preferred LLM provider/model, per-generation cost ceiling, and any content/compliance constraints on AI-authored copy?
  4. Domain & infra ownership. Is the builder domain owned? Do we have Cloudflare-for-SaaS and S3-compatible accounts, or include procurement?
  5. Templates & theming freedom. How many starter templates for MVP, which industries, and how much theming freedom (fixed palettes vs. free color/font choice)? Any FieldPie brand kit?
  6. Scale & cost targets. Expected tenants/custom domains in year one? Informs when the self-host path becomes relevant.
  7. Compliance/data residency. Any regional data-residency / PII requirements affecting DB region and storage?
